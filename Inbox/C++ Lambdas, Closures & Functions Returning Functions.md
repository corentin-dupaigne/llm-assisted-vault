
## 1. The idea: currying

A function of two arguments `f(a, b)` can be rewritten as a function of **one** argument that **returns another function** of one argument:

```
f(a, b)      →     g(a)(b)
```

- `g(a)` does not compute the final result. It returns a *new function* that "remembers" `a`.
- Calling that returned function with `b` produces the result.
- You can stop halfway: keep `g(a)` in a variable and call it later with different `b` values.

This is called **currying** (or partial application when you fix only some arguments).

> [!question] Think about it
> If the returned function needs `a` later, *where* is `a` stored once `g` has returned?
> → Answer in section 4 (closures).

## 2. Lambda syntax

```cpp
[captures](parameters) -> return_type { body }
```

| Part | Role | Optional? |
|---|---|---|
| `[captures]` | Which variables from the surrounding scope the lambda can use | No (can be empty `[]`) |
| `(parameters)` | Like a normal function's parameters | Yes if none |
| `-> return_type` | Explicit return type | Yes, deduced from `return` |
| `{ body }` | The code | No |

Example (one level only):

```cpp
auto square = [](int x) { return x * x; };
square(4); // 16
```

- A lambda is an **expression**: it produces an object (a *closure object*).
- That object has an `operator()`, so it can be called like a function.
- `auto` is needed (or `std::function`, see §5) because each lambda has a **unique, unnamed type** generated by the compiler.

> [!note] Immediately calling a lambda
> `[](int x) { return x + 1; }(3)` creates the lambda **and** calls it at once → `4`.
> Similarly, if something *returns* a callable, you can chain calls: `something(1)(2)`.

## 3. Captures

A lambda body **cannot** see local variables of the enclosing scope unless they are captured.

```cpp
int factor = 10;
auto f1 = [](int x) { return x * factor; };       // ❌ error: factor not captured
auto f2 = [factor](int x) { return x * factor; }; // ✅ copy of factor
auto f3 = [&factor](int x) { return x * factor; };// ✅ reference to factor
```

| Capture | Meaning |
|---|---|
| `[]` | Nothing captured |
| `[x]` | `x` copied **by value** into the lambda when it is created |
| `[&x]` | `x` accessed **by reference** (the original variable) |
| `[=]` | Everything used is captured by value |
| `[&]` | Everything used is captured by reference |
| `[x, &y]` | Mixed |

### By value vs by reference — when the capture happens

```cpp
int n = 1;
auto byVal = [n]() { return n; };
auto byRef = [&n]() { return n; };
n = 42;
byVal(); // 1   (copy taken at creation)
byRef(); // 42  (reads the current n)
```

> [!warning] Dangling references
> A reference capture is only valid **as long as the referenced variable is alive**.
> A function's **parameters and local variables are destroyed when the function returns**.
> If a lambda that captured them by reference *outlives* the function → **undefined behaviour** (garbage values, crashes, or "it works on my machine").
>
> Rule of thumb: **if a lambda escapes the scope it was created in (returned, stored, passed elsewhere), capture by value.**

> [!question] Think about it
> In the exercise, the inner lambda is returned out of the outer lambda's call. What happens to the outer lambda's parameter at that point? Which capture mode is safe?

### Globals don't need capturing
Variables with **static storage duration** (globals, `static` locals) are not captured: they're simply accessible. Only *automatic* (local / parameter) variables need capturing.

## 4. Closures

A **closure** = the function code **+** the captured state.

Conceptually, the compiler turns a capturing lambda into a small class:

```cpp
// [factor](int x) { return x * factor; }   becomes roughly:
struct __Lambda_unique_name
{
    int factor;                          // captured copy
    int operator()(int x) const { return x * factor; }
};
```

- Each time the lambda expression is **evaluated**, a **new object** is created with its own copy of the captured values.
- So two closures built from the same lambda expression with different captured values behave differently.
- `operator()` is `const` by default → captured-by-value variables are read-only inside (use `mutable` to modify the copy; not needed here).

This answers the question of §1: the "remembered" value lives **inside the returned closure object**.

## 5. Return type deduction & `std::function`

### 5.1 `auto` deduction
A lambda's return type is deduced from its `return` statement(s). If a lambda returns *another lambda*, the deduced return type is that inner lambda's unique closure type — fine, as long as nobody needs to write it down.

```cpp
auto make = []() { return [](int x) { return x; }; }; // returns a closure type
```

All `return` statements in one lambda must deduce to the **same** type.

### 5.2 `std::function` (header `<functional>`)

A **type-erased** wrapper able to hold *any* callable with a given signature:

```cpp
#include <functional>

std::function<R(Args...)>
```

Read it as: "something callable taking `Args...` and returning `R`".

```cpp
std::function<int(int)> f = [](int x) { return x * 2; };
std::function<int(int, int)> g = [](int a, int b) { return a + b; };
std::function<std::string(int)> h = [](int n) { return std::to_string(n); };
```

Key properties:
- Lambdas, function pointers, functors… all convert to a `std::function` with a compatible signature.
- Gives a **nameable type** → can appear in a header, as a variable type, a parameter, a return type.
- Cost: a small runtime overhead (indirect call, possible heap allocation). Irrelevant here.

### 5.3 Nesting signatures
The `R` in `std::function<R(Args...)>` can itself be a `std::function`. To read a nested type, **work from the outside in**:

```
std::function< RETURN_TYPE ( PARAMS ) >
                    ↑
         may itself be std::function<...>
```

Example (unrelated to the exercise): a callable taking a `std::string` and returning "a callable taking nothing and returning `bool`":

```cpp
std::function<std::function<bool()>(std::string)>
```

## 6. Declaring a variable in a header, defining it in a `.cc`

The exercise asks you to store the lambda **in a variable**, whose declaration is in the `.hh` and definition is in the `.cc` you submit.

### `extern` declaration vs definition

```cpp
// something.hh
extern int counter;          // declaration: "exists somewhere", no storage

// something.cc
#include "something.hh"
int counter = 0;             // definition: storage + initializer, exactly ONE
```

- **One Definition Rule (ODR)**: a non-inline global variable must be *defined* in exactly one translation unit. Defining it in a header included by several `.cc` files → multiple-definition link error.
- The definition's type must **match** the declaration exactly.
- Consequence: if the header declares the variable with an explicit type (e.g. a `std::function<...>`), your `.cc` definition must use that same type; you can't use `auto` for an `extern` object whose definition must match a declared type.
- Alternative you may see: C++17 `inline` variables (`inline T x = ...;` directly in the header). Check which form the provided header uses and follow it.

> [!warning] Don't modify the provided header
> Only `forward_multiplication.cc` is submitted: your code must work with the `.hh` as given.

### Initializing a global with a lambda
A global can be initialized with any expression, including a lambda expression. Note that a lambda defined at **namespace scope** has nothing local to capture: its capture list is empty. Captures only become relevant for lambdas created *inside* another function/lambda body.

## 7. Compilation flags to keep in mind

`-Wall -Wextra -Werror -pedantic -std=c++20 -Wold-style-cast`

| Flag | What can bite you |
|---|---|
| `-Werror` | Every warning is a compile error |
| `-Wextra` | **Unused parameters** and unused captures are warnings → errors |
| `-Wold-style-cast` | `(int)x` forbidden; use `static_cast<int>(x)` if you ever need a cast |
| `-pedantic` | No compiler extensions |

> [!note]
> Clang warns on an **unused lambda capture** (`-Wunused-lambda-capture`). Capture only what you actually use.
